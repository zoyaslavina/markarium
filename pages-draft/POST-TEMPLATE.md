# Journal post template

## Publication record

- **Working title:** `{{POST_TITLE}}`
- **One-sentence premise:** `{{POST_PREMISE}}`
- **Status:** idea / outline / draft / verified / published
- **Publication date:** `{{POST_DATE}}`
- **Related release or commit:** `{{REFERENCE}}`
- **Category:** product / anchoring / accessibility / agents / privacy / architecture / release

## Article outline

1. **The concrete problem** — begin with the user or development situation, not a feature announcement.
2. **What was observed** — explain the failure mode or constraint with a safe, non-private example.
3. **The design decision** — describe the selected approach and meaningful alternatives.
4. **What changed** — state verified behaviour without overstating conformance or security.
5. **Limitations** — name browser differences, unresolved cases and edition boundaries.
6. **What this suggests** — close with the broader lesson or the next question.

## Pre-publication checks

- [ ] Product name, version, dates and links are final.
- [ ] Every claim matches shipped behaviour and `FEATURES.md`.
- [ ] No private document content, filenames, local paths, tokens or personal metadata appear.
- [ ] Screenshots use fictional content and have useful alternative text.
- [ ] Headings form a clear outline; link text makes sense out of context.
- [ ] The post distinguishes automated checks from human accessibility testing.
- [ ] Planned app work is labelled as planned.
- [ ] Third-party facts or quotations have direct sources and respect quotation limits.
- [ ] The page works without JavaScript and makes no third-party request.
- [ ] Canonical, title, description and share metadata are unique.
